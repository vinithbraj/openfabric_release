How Parameter Context Is Used

Keep executable connection details, tokens, paths, IDs, and generated discovery data in value_json. Put non-secret domain guidance in context_json. Normal agent prompts receive bounded summary and prompt guidance; the clarification resolver receives matched concepts, metrics, relationships, and clarification guidance when it is deciding whether to ask the user or continue with a high-confidence assumption. Context helps the agent choose better entities, but it never bypasses validators, SQL safety, credential handling, join warnings, or mutation approvals.

Value JSON

Enter the executable payload the runtime may actually use: hosts, ports, usernames, passwords, tokens, paths, service IDs, database names, and generated SQL metadata such as schema_catalog, relation_foreign_scheme, and schema_discovery. Sensitive entries stay masked until Reveal is used. This JSON can be converted into runtime execution values and shell environment names, so do not put prompt-only notes here.

Context summary

Write a short plain-language description of what this parameter represents. This appears in masked UI summaries, audits, parameter matching, and compact prompt context. Good examples: "Canonical DICOM/RT oncology database" or "Production GitHub deploy key for the imaging repo." Keep it non-secret and concise.

Prompt guidance

Add compact instructions that should be included when this parameter is relevant to a normal agent prompt. Use this for stable domain rules, preferred terminology, default interpretations, query-shaping rules, or workflow conventions. For SQL profiles, include bounded guidance such as "rtplans maps to RTPlan" or "patient counts should use a scalar outer count over grouped patients."

Clarification guidance

Add richer guidance for moments when the agent is about to ask the user a question. The typed clarification resolver uses this, along with candidate tables/files/options and the current clarification mode, to decide whether to ask or continue with an assumption. Use it for "do not ask if..." rules, synonym handling, ambiguity thresholds, evidence fields to inspect first, and cases where the user must be asked.

Concepts JSON

Enter a JSON array of domain concepts the agent should recognize. Each object can include concept_id, display_name, one_line_definition, user_phrases, synonyms, and preferred evidence such as tables, columns, files, or option values. These concepts are used for parameter matching, SQL/entity selection, and clarification auto-resolution.

Metrics JSON

Enter a JSON array of reusable metric definitions, cohorts, thresholds, formulas, or aggregation rules. Useful fields include metric_id, display_name, one_line_definition, user_phrases, formula, default_threshold, and preferred_aggregation. The agent can use these to turn vague reporting requests into concrete plans without asking unnecessary clarifications.

Relationships JSON

Enter a JSON array of semantic relationships that help the agent understand how concepts, tables, files, services, or workflows relate. For SQL, these are prompt and clarification evidence only: they can help generate a sensible read-only join and explain warnings, but they do not become DB-approved foreign keys and cannot bypass SQL validation.

Advanced context

This is the full raw context_json object. The structured fields above are synchronized into user_provided_domain_context. Use this area only when you need to inspect or edit advanced non-secret metadata while preserving the canonical shape. Invalid JSON will block saving context but will not reveal or modify masked secrets.
